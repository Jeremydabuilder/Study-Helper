# Independent review: personal ChatGPT connection

Reviewer: Claude (separate from the implementer, Codex). Reviewed `codex/chatgpt-personal` @ `e99635b` against `claude/pilot-integration` @ `e262ba6` (which is an ancestor). Fixes are on `claude/review-personal-chatgpt`; nothing was pushed to Codex's branch or merged.
All checks below use fake accounts and mocked responses. **No real sign-in, credential, spend, deployment or invitation was involved, and nothing here establishes live functionality.**

## What I could and could not confirm about the protocol
`developers.openai.com` and `help.openai.com` could not be fetched from the review environment (host not allowed), so I could not read the SIWC pages in full. I confirmed the shape of the protocol from the search excerpts of OpenAI's own pages (Overview, Registration and sign-in, Preview limitations, Errors and recovery, the cookbook article, Sign in with ChatGPT Terms, Help Center article 20001542):
- Confirmed (excerpts): the open-source "local app / personal project" path exists and is separate from the commercial trial; first sign-in uses `client_id=dynamic_agent_client`, the app must save the **issued** `client_id` (`oaiapp_…`) and a stable `ext_agent_host_id`; scopes `offline_access resource.invoke chatgpt.tokens.use.direct`, resource `https://api.openai.com/v1`; each client is bound to one user **and workspace**; plan usage is enabled only when the granted scopes include `chatgpt.tokens.use.direct`; over HTTP requests need `store: false`, `stream: true`; `background, conversation, max_output_tokens, max_tool_calls, metadata, moderation, multi_agent, prompt, prompt_cache_retention, safety_identifier, temperature, top_logprobs, top_p, truncation, user` are rejected and `previous_response_id` must be omitted (error `subscription_sharing_unsupported_capability`, do not retry); the app renews the token itself; `refresh_token_reused` / `refresh_token_invalidated` mean clear the tokens and sign in again with the saved client ID; `invalid_client` means fix the configuration; terms forbid asking for ChatGPT passwords or session cookies. **The protocol is still supported as far as these excerpts show.**
- **Not confirmable from here** (so labelled live checks below): the exact authorize/token/JWKS URLs and issuer string used in `src/server/personal/chatgpt.ts` (lines 7–10), the redirect-URI rule for loopback ports, the exact response shape of the models endpoint (`{models:[{slug,display_name,visibility}]}`, lines 118–119), whether the inference route wants any extra header such as the host id, and OpenAI's current UI/button guidelines.
- The implementation uses no undocumented ChatGPT backend endpoint, no Codex client id and no credentials from other apps: confirmed by reading every network call (`auth.openai.com` authorize/token/JWKS, `api.openai.com/v1/models`, `api.openai.com/v1/responses`).

## Findings (most severe first). Each has a failing test that now passes
All line numbers refer to `e99635b`.

1. **Medium — a renewal can throw away the rotated tokens and force a reconnect** (`personal/chatgpt.ts:107` with `:124`). The renewal result is dropped when `this.credential !== c`, but `selectModel` replaces the credential object. Reproduce: sign in, start `selectModel` (waits on the model list), let the token expire, start a renewal, let the model list return, then let the token endpoint answer. The provider has already rotated the refresh token, the app refuses to save it, and the connection is dead. Impact: forced reconnect, at the worst moment. Fix (applied): renew into the *latest* credential, protected by a generation counter that disconnect **and a new sign-in** advance; `welcome()` no longer mutates in place. Tests: "model selection finishing while a renewal is in flight…", "a sign-in that completes while a renewal is in flight is not overwritten…".
2. **Medium — no renewal margin and no recovery from a refused token** (`personal/chatgpt.ts:96`, `ai/chatgpt.ts:30,60`). A token is used until the exact millisecond it expires and a 401 only produces "Reconnect your ChatGPT account". Reproduce: 5 s left on the token → the request goes out with it; a revoked/just-expired token → permanent error message although renewal would work. Impact: intermittent failures that look like lost authorization. Fix (applied): renew when under 60 s remain; on 401 renew once and resend the same request (a refused request is not billed); a second 401 stops with the reconnect message. Never any fallback provider. Tests: "renews a token that has under a minute left…", "a request answered 401 renews once…".
3. **Medium — a provider-ended sign-in leaves the app claiming to be connected** (`personal/chatgpt.ts:66,99–112`). Every non-OK token response became the same "expired or declined" error; the dead credentials stayed, the banner said "Using ChatGPT plan", and every study request retried the dead token. OpenAI's documented recovery is to clear the tokens and sign in again with the saved client. Fix (applied): `refresh_token_reused`, `refresh_token_invalidated`, `refresh_token_expired`, `invalid_grant` clear the tokens, keep the account binding, drop the plan provider and tell the page; temporary failures (5xx, network) keep the sign-in; `invalid_client` has its own message. Tests: three terminal shapes + "a temporary provider failure… keeps the saved sign-in".
4. **Medium — the saved sign-in is not really "owner-only" on Windows, and the default folder may be synced** (`personal/chatgpt.ts:39–48`, docs). `chmod 0600/0700` does nothing on Windows; the default folder is `./data/chatgpt-auth` inside the repository, which on a typical Windows PC is under OneDrive/Documents sync; tokens are plain JSON. Impact: a long-lived refresh token can be copied to cloud storage or be readable by other accounts. Fix (applied): on Windows the folder is restricted with `icacls` to the current user and SYSTEM (best effort, warns if refused); a folder that looks cloud-synced blocks starting a sign-in and Settings explains how to move it (`CHATGPT_AUTH_DIR`); real Windows instructions in `docs/PERSONAL_CHATGPT.md`; the plain-JSON storage and the "only use on a computer you alone use" caveat are now stated. Tests: `syncedFolderWarning`, `restrictToCurrentUser` with an injected runner. **The icacls call itself has not been run on Windows: live check.**
5. **Medium (live risk) — the sign-in return could be refused by the Origin check** (`app.ts:80`). Every request with an `Origin` header must match the Host. After OpenAI's redirect (especially if its page redirects a form POST) a browser may send `Origin: https://auth.openai.com` or `null` on the final GET, which would answer 403 and break sign-in on the real service while every mock passes. Fix (applied): the single route `GET /auth/chatgpt/callback` skips the Origin comparison (the Host check stays); it is protected by the one-use state, the browser-bound cookie and the nonce, and a test shows every other route still refuses a foreign Origin.
6. **Medium (live risk) — an answer could be empty although the stream completed** (`ai/chatgpt.ts:54`). Text was read only from `response.completed.output`. If the completed event does not repeat the output items (they were streamed as `response.output_item.done`), the transport returns `''`, the app treats it as an empty answer and retries (two plan requests). Fix (applied): use the streamed items only when the completed event has none, and only after `response.completed` with status `completed`; partial text is still never success. Test: "the answer text is taken from output items…".
7. **Low — a forged link can cancel a real sign-in** (`personal/routes.ts:20`). The callback cleared the browser cookie before checking it, so any page that navigates the browser to `/auth/chatgpt/callback?state=x` removes the cookie and the real return then fails. Fix (applied): the cookie is cleared only for the genuine attempt (`matches()`).
8. **Low — Settings loses the reason, repeats stale notices, and can spin forever** (`Settings.tsx` ChatGPTAccount). Every failure said the same thing (the "different account" explanation was computed and discarded), the `chatgpt=failed` notice stayed in the address bar, and a failed status request showed an endless spinner. Fix (applied): a safe reason code (`account_mismatch`, `permission`, `cancelled`, `expired`, `storage`, `generic`; never a token, code or claim) selects the message, the notice is shown once and removed from the address, status errors show a retry. e2e tests added.
9. **Low — the "inconsistent/unreadable" startup errors tell you to do something you cannot do** (`personal/chatgpt.ts:45,47`: "Disconnect it", while the app refuses to start). Reworded to the real remedy (delete the `chatgpt-auth` folder); documented how to change accounts deliberately. Also: a port already in use now prints a clear message; `npm run personal` checks the Node version.

### Reported, not changed (judgement or live-only)
- **Registration is not saved before the code exchange** (`chatgpt.ts:77–79`). OpenAI's excerpt says the issued client id should be saved first so a failed exchange can reuse it. Today a failed first exchange leaves an orphan registration and the next try registers again. Safe, untidy; changing it relies on server behaviour I cannot test.
- **Any program or user on the same computer can use the connection through `127.0.0.1`** (no login in local mode). Documented; the feature is for a computer only you use.
- **Two Study Helper processes on one connection folder** invalidate each other's rotating token. Documented.
- **`npm run personal` rebuilds every start and rewrites the tracked `dist-server` bundle**, so the working tree shows changes. Harmless, noisy.
- **One 45 s timeout covers the whole stream**; long reasoning answers may need `AI_TIMEOUT_MS`.
- A stream whose last event lacks the closing blank line is treated as incomplete (fails safe).
- The tokens are not encrypted at rest; protection is the folder permission only.

## Verified by test or inspection (mock-level)
Account/client substitution refused (different subject, different client, no client id at registration); state, browser-bound cookie, nonce, 10-minute expiry and single use enforced, forged callbacks leave the pending attempt intact; scopes `chatgpt.tokens.use.direct` and `resource.invoke` required at sign-in and renewal; ID-token signature, issuer, audience, expiry, subject, nonce checked with `jose` (tampered/impostor/expired rejected in tests); binding survives disconnect and restart; tokens never in status/routes/errors (damaged-file test shows the secret is not echoed); credentials never copied from ChatGPT/Codex profiles (no file other than `DATA_DIR/chatgpt-auth` or `CHATGPT_AUTH_DIR` is read); hosted and guest modes refuse `AI_PROVIDER=chatgpt` (also verified by starting the real bundle: exit 1, "personal and local only"); loopback-only Host and cross-origin POST refused (verified on a running server); request body is exactly `model, instructions, input, store:false, stream:true`; partial output after a usage error, `response.incomplete`, and dropped streams are failures; unselected model, attachments (OCR) refused before any request; with `AI_PROVIDER=chatgpt` there is no path to Anthropic, Groq or an API key (`buildProvider` returns `null`, i.e. offline templates); plan calls carry zero estimated dollars but keep the local daily request allowance.
